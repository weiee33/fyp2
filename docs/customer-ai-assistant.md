# Local Life AI assistant

The centre navigation button opens the customer assistant with an upward transition. Existing Explore, Bookings, Notifications and Profile routes retain their logical indices. The legacy chatbot route now opens the same implementation.

## Customer features

- Create, select and delete private conversations; load earlier messages and older chats.
- Attach a gallery/camera photo, preview it, and send it with an optional question. Images are re-encoded to JPEG, resized to 1600 pixels, stripped of EXIF and limited to 4 MB.
- Hold the microphone to dictate, release to stop, then review/edit and send the words. Recognition uses the device speech service and requires microphone/speech permissions; availability depends on the device and language.
- Ask AI compares actual published services, provider ratings/review counts, prices, available appointments and saved addresses. Nearby recommendations use published service centres/coverage, not live provider tracking.
- Do it for me can open supported app screens automatically. Booking requests, cancellation and default-address changes show a concrete confirmation card before writing. Payment is always opened and completed by the customer.

Supported navigation: services, bookings, notifications, profile, addresses, reviews, an owned booking, a verified provider and the customer's checkout. This is a bounded app assistant, not arbitrary screen control or a background voice wake-word service. Voice output and streaming model text are not implemented.

## Configuration and deployment

1. Create a Gemini API key in Google AI Studio: https://ai.google.dev/gemini-api/docs/api-key.
2. Save `GEMINI_API_KEY` in Supabase Project Settings / Edge Functions / Secrets. Never put it in Flutter, Git, a screenshot or chat.
3. Optional `GEMINI_MODEL` overrides the tested default `gemini-3.5-flash-lite`. Choose a Gemini model supporting images and function calling. See https://ai.google.dev/gemini-api/docs/models.
4. Apply migrations in order, then deploy `customer-assistant` with JWT verification enabled. It imports `_shared/customer_ai.ts` and uses the built-in Supabase URL, anon and service role environment values.
5. Build/install the app and log in as an active verified customer. Provider/admin sessions do not have customer assistant access.

This project was deployed with migrations `20261013030453_customer_gemini_assistant` and `20261013030827_customer_ai_action_history`. Their repository versions match remote migration history to avoid Supabase Preview drift. On 13 October 2026 a protected, temporary connection probe returned HTTP 200 / `READY` from Gemini using the configured secret and actual function declarations. The probe was then replaced with a JWT-protected HTTP 410 response; it no longer reads secrets or calls Gemini. The deployed assistant requires a real customer session; no customer password was accessed for setup testing.

Gemini access, quota and charges follow the Google project's selected tier. App limits are abuse controls, not a guarantee of zero cost. No Google billing configuration was changed.

## Trust boundaries and privacy

The Edge function validates the bearer with Supabase Auth. All customer reads and prepared actions run under that user's JWT. Gemini sees only declared tools, with strict allowed arguments; it never receives database credentials or payment credentials. Only the server can persist assistant responses. No tool confirms an action or submits a payment.

Messages, attached photos and relevant app data are sent to Gemini, as disclosed in the UI. Address lookup for recommendations omits street address and contact information; actual booking cards are generated by the database and display the full address to the customer. User-entered messages/photos may themselves contain personal details. Only the latest 20 messages and latest two attached photos are included in a turn. Deleting a conversation erases its messages/action drafts and removes photos through the Storage API; account deletion also erases AI content. Submitted bookings remain part of the normal booking record. Gemini-side retention is governed by Google's API terms.

Tables live in the private schema with RLS and no client table grants. Explicit RPCs enforce active-customer ownership. The private image bucket restricts reads/writes to the owning conversation, blocks overwrites and disallows reading deleted conversations. Service credentials are used only for response persistence/failure and photo cleanup. Deletion invalidates outstanding worker leases so a late response cannot restore removed content.

Booking confirmation delegates to the existing authoritative booking function, preserving availability, provider eligibility, idempotency and payment rules. The action expires after 15 minutes. Price, duration and address snapshots must still match before confirmation; changed details require a new card. Retried confirmations return the existing result. History resolves current completed/expired action state instead of displaying an old pending label.

Limits: 4000 characters per message, 400 messages/conversation, 100 active conversations/customer, 200 stored photos/customer, 60 model attempts/customer/24 hours, six recent turns/minute, three attempts/request, 30 action drafts/conversation/hour, five model rounds and 12 tool calls/turn. The project-wide 2000-attempt rolling guard is approximate under concurrent different customers; provider quota/budget controls remain necessary. Failed requests preserve the draft and reuse an immutable request ID for safe retries.

## Validation and device acceptance

Automated coverage includes authentication, secret isolation, tool allowlisting, thought-signature round trips, replay without another model call, no automatic payment/booking mutation, photo retry, speech hold/release, deletion confirmation, navigation and database ownership/idempotency/deletion/stale-summary safeguards. Database fixtures execute in a transaction that is rolled back. Existing customer/payment tests are included in the full suite.

On a physical Android/iOS device, verify:

1. Tap the centre AI button; send a service question and receive a live reply.
2. Hold the microphone, speak, release, edit the words and send. Test permission denial as well.
3. Send a gallery photo and a camera photo; reopen history and check the private previews.
4. Ask for a real available service at a saved address/date/time. Review the actual quote before confirming. Confirm only once; the resulting booking must be Pending provider acceptance, with no payment submitted.
5. In Do it for me, ask to open bookings. Ask to open payment and verify it remains a manual action.
6. Delete the test conversation and verify it disappears while its submitted booking remains.

Camera, microphone and live customer-session booking acceptance need device verification. Automated mocks and the Gemini readiness response do not substitute for those checks.

Supabase's informational `rls_enabled_no_policy` notices for the four private AI tables are intentional deny-all direct access; only checked RPCs access them. See https://supabase.com/docs/guides/database/database-linter?lint=0008_rls_enabled_no_policy. Existing warnings for admin invitation lookup and disabled leaked-password protection are unrelated to this assistant change.
